## 1. Enforce the versioned file contract before deriving a preview

In `scripts/backup-preview.js`, `distinguishNonBackup` only rejects an incorrect kind when it is a string. `kind: null` or a numeric kind reaches `validateParsedBackup` and is accepted if formatVersion is 1. Independently reproduced `kind: null` as `ok: true`, `complete: true`, no inconsistencies.

`validateStore` defaults missing `data` to `{}` and missing `loadState` to `ok`. Removing both from a valid answers store produces an accepted, complete empty store, although the required source data is missing. Count warnings do not make that a valid empty backup. Also, `LOAD_STATES[store.loadState]` accepts inherited property names such as `toString` as supported states. Reproduced `loadState: "toString"` accepted unchanged.

Require exact kind and version, own required store fields and explicit allowed loadState values. Enforce the documented required data/status fields or explicitly revise the format contract with a justified compatibility rule; never turn absent source data into known empty data. Validate ambiguity items' required value and candidate/status structure rather than manufacturing missing metadata. Keep actual ENG-006a downloads compatible. Add tests for null/numeric/missing kind, absent data/loadState, inherited-property names, and malformed ambiguity items. Validate by own properties or explicit equality, not prototype-chain membership.

## 2. Compare duplicated ambiguous-answer content, not just key names

Near `claimedKeys` in `validateParsedBackup`, only item key names are compared. Changing the top-level duplicate's value while retaining the same key produces no inconsistency. Reproduced using one retained item: answers-data value `SYN-original`, duplicate value `SYN-conflicting`; accepted with an empty inconsistency list.

Detect divergent values, candidate lessons, status and relevant metadata. Keep the answers-data copy authoritative and unassigned, and surface the mismatch. Candidate lesson order is documented as unordered, so reordering alone need not produce a false conflict. Add cases with identical keys and differing content, not just added/removed item keys.

## 3. Do not treat unreadable destination storage as empty

`buildPreview` compares only `currentDevice.stores[id].data`. It ignores the destination's loadState/writable status even though `currentBackupInput()` supplies them. With a complete backup and an answers destination of `{loadState: "malformed", writable: false, data: {}, originalRaw: "SYN-unreadable"}`, the preview reports backup-only entries, zero conflicts and a proposed future add, without flagging that stored destination answers cannot be compared.

Keep source completeness separate from destination readability. Mark comparison against unreadable/unavailable destination stores as incomplete or unknown, clearly preserve their existing write guards and raw evidence, and do not label possible stored matches/conflicts as absent. The preview may compare available in-memory values, but must explain that limitation. Add pure-module and actual failed-load browser assertions for this wording and comparison status, alongside unchanged learner data/guards. No restore writes.

## 4. Ignore stale asynchronous file reads

`onBackupFileSelected` has no read-generation/cancellation guard. A prior File.text promise can render after a newer selection and after the user closes the preview. Confirmed in Chrome through the actual input with a deferred File.text only for a synthetic fixture:

1. Select valid `SYN-slow.json`; defer its File.text resolution.
2. Select malformed `SYN-new-invalid.json`; its error preview opens.
3. Close the new preview; confirmed closed.
4. Resolve the first read. The overlay unexpectedly reopens and shows `SYN-slow.json`.

Learner state remained unchanged in that experiment, but the UI displays a superseded file and defeats cancellation. Use a monotonically increasing selection/read token or equivalent cancellation mechanism. Invalidate on new picker/selection, cancel/close and relevant navigation. Ignore stale success AND failure callbacks in both File.text and FileReader paths. Test slow-first/fast-second, close-before-resolution, stale failure and fallback-reader cases. Observe the actual modal/filename and learner state, not only the page's test marker.
